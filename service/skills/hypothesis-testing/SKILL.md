# 假说验证与缺陷排查

适用于偶发、跨系统或有多个合理解释的缺陷。原因与修改点已经明确时，直接进入局部修复和验证，不必额外列假说或重新建立现象基线。

## 从当前缺口开始

先使用用户提供的复现条件、日志和显式设置 `keepInCalls=true` 后由 Runtime 记录到 workspace 中的执行事实。只补影响下一步判断的信息，例如触发输入、首个相关错误、出现问题的环境差异。已有失败用例可以直接作为基线。

把不确定点写成可验证的预测：如果原因是 X，在条件 A 下应观察到 B。只保留当前证据支持的候选解释，不凑数量，也不要求排除所有可能原因才能修改。

按问题选择工具：

- 数据契约不清：查看实际请求或返回样本，核对字段和值；用 `network_grep`、`har` 或本地读取工具。
- 时序或生命周期不清：观察相关事件、变量和错误堆栈；用 `see_console`、`page_eval_expr`，或在相关分支加临时日志。
- 环境差异不清：只对比与现象有关的配置、版本、缓存或登录态。
- 边界行为不清：写一个能触发该输入的定向测试。测试失败是有效证据，用它选择修复点。

需要源码时先定位相关函数和调用位置，再读实际需要的原文。返回被外置时，用 `evidence_search` 的 `keyword` 找块，再用来源调用和 `blockId` 取回完整原文。

## 何时动手

当证据已指向具体行为、目标代码和预期结果，并且有办法验证改动时，就实施局部修复。尚未解决的其他问题单独记录，不阻塞已具备条件的部分。

如果暂时无法判断修复方向，选择一次能区分候选解释的观测或小实验。探针可以是只读检查、单点日志、最小测试或可回退的局部修改；不为验证一个猜想重写整片代码。

## 用反馈收敛

1. 运行直接覆盖该行为的测试或复现场景，对照预期结果。
2. 若失败，读取具体失败输出，区分假说错误、实现错误和环境阻塞，再修正对应部分。不要原样重复同一批读取。
3. 若通过，检查受该改动直接影响的相邻行为；满足本次验收条件后收口，不为了证明“唯一根因”继续扩大排查。

复用显式设置 `keepInCalls=true` 后由 Runtime 记录到 workspace 中的执行事实，并参考动态 <runtimeNotices> 提醒。交付时说明修复依据、已验证行为及未验证部分。
