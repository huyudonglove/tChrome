# 源码与真实浏览器对照

适用于页面功能验收，以及登录、表单、上传下载、异步状态或视觉结果与源码预期不一致的问题。纯函数或工具内部逻辑可用定向测试验证，不因为有浏览器环境就扩大成全站审计。

## 围绕目标行为形成预期

从用户要求和已有证据选一个待验证行为，写清输入、动作和预期结果。已具备预期与定位信息时直接操作或修改。

源码检查只选回答当前问题所需的部分：

- 导航问题：对应入口的 `href` / 路由配置；grep 没命中不等于不可达，必要时实际打开。
- 表单问题：目标字段、校验、提交接口及相关成功或失败分支。
- 接口问题：相关 baseURL、代理或鉴权注入；仅在怀疑连通性差异时比较直连与代理请求。
- 渲染或状态问题：相关组件、状态来源和生命周期。

用 `local_fs_search` / `local_fs_grep` 定位，按需 `local_fs_read`。外置结果通过 `evidence_search` 的 `keyword` 定位、`blockId` 读取完整原文。解析或匹配结构尚不清楚时，读取一个真实样本或建立复现测试即可，不反复重新确认已知结构。

## 选择合适的运行环境

用 `list_tabs` / `tabs_current` 选择目标标签，优先使用用户已有的页面。依赖登录态、扩展、SDK、WebGPU/Canvas 或视觉呈现的结论，在具备这些条件的真实 Chrome 中验证。

无头浏览器可做批量结构和连通性检查；它的 profile、登录态和扩展可能不同，因此失败先作为线索，不直接当成真实用户环境的故障。真实环境不可用时，继续完成源码检查或可运行测试，并报告未验证部分。

若外部脚本确需连接真实 Chrome，可检查调试端口和 `/json/version`；连接条件不成立时，使用现有浏览器工具，不持续尝试拼接同一连接方案。

## 操作、观察、修正

1. 用 `open_url` 导航；按目标条件选择 `wait`、`wait_response` 或 `wait_network`。超时后检查具体状态，避免将加载占位当作最终页面。
2. 目标明确时直接用 `page_click_role`、`page_fill_role`、`page_submit_wait`、`combo_select` 等复合工具操作。需要定位时，再用页面概况、控件列表或局部检查补充信息。
3. 用 `page_assert` 断言预期，`page_recheck` 查看实际状态；接口用 HAR 或响应工具，运行时错误用 `see_console`，页面状态用 `page_eval_expr`。画面结论用 `capture_page`，小控件优先局部截图。
4. 不一致时记录“预期、实际、差异位置”，实施有依据的局部修改，再重复直接相关的操作或测试。不同问题分别推进，不让一个未解决分支阻塞其他已明确的修复。

提交表单、上传、删除、对外发消息和账号资金操作需有用户对该动作的明确授权。已有授权覆盖当前动作时继续执行；执行后验证实际结果，不把点击成功当成业务成功。

## 按问题选择验收项

表单边界值、加载失败、空态、并发操作、跨页状态、多视口和第三方失败都是可选验收方向，按改动影响范围选取，不要求每次全部跑一遍。视口或环境差异可用 `fingerprint_read` / `fingerprint_apply` 验证；Canvas/WebGL 可结合状态探针和截图。

检查记录是否落盘时，可用唯一标记写入后读取实际记录，避免仅凭窗口摘要推断原始调用参数。批量脚本逐项输出结果，保留相关失败详情，减少无关长日志。

每批工具结果按 workspace 要求记录，页面状态用 `observation_write` 固化。满足目标验收条件后收口，说明源码核对、真实浏览器实测和其他测试各自证明了什么；失败和未覆盖条件如实报告。
