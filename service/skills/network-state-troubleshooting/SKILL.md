# 网络与异步状态故障排查

适用于重复请求、翻页跳动、状态倒退、响应覆盖或失败后持续重试等问题。围绕用户报告的操作和相关请求排查；无关接口失败不作为当前修复的前置任务。

## 建立一段可解释的事件链

从已知异常开始，记录触发操作、相关请求和异常状态。用 `har` 获取请求序列，或用 `network_grep` 定位目标接口；需要等待本次动作结果时使用 `wait_response` 或 `page_submit_wait`。

查看网络日志时把以下信息放在一起，避免只凭参数或时序归因：

- 时间与耗时，用于判断先后和并发。
- 请求方法、URL 和影响行为的参数。
- HTTP 状态及响应体中的相关业务字段。

先检查异常发生前后的相关请求。只有范围仍不明确时，才扩大到状态码分布、业务错误码或其他接口。区分相关失败与统计服务、外部资源等噪声，不要求核验全部异常接口后才能继续。

## 选择能区分原因的检查

常见线索包括：

- 成功响应更新数据后又发起请求：检查依赖项变化、重渲染、滚动观察器或监听器是否重复触发。
- 失败后游标或列表回到初始态：定位 `catch`、`onError`、fallback 或 reset 相关代码，核对失败分支如何改变状态。
- 较早响应覆盖较新结果：对照请求顺序、完成顺序和实际写入状态，检查并发与取消语义。
- 页面离开后仍有回调：核对事件注册、卸载和后台任务生命周期。

这些是候选方向，不是必须逐项排查的清单。证据指向其中一条时沿该调用链验证；证据不符时调整解释，不强行归入固定模型。

## 局部修复与验证

已确定触发条件、状态变化和预期行为后，修改对应逻辑并运行定向验证。按项目已确认的失败、重试、清理和恢复语义实现，不自行增加熔断、重试层或新的状态规则。其他独立问题可分别推进。

修复失败路径时，用相关错误响应验证；修复竞态时，控制响应顺序或事件时序验证。再检查直接受影响的正常路径。测试未通过就依据实际结果修正代码或判断，不以静态阅读代替运行反馈。

查看源码被外置时，用 `evidence_search` 搜索并读取对应 `blockId` 的完整原文。每批结果按 workspace 要求记录已确认的请求链、状态变化、源码位置和验证结论；无新证据时更换能回答缺口的检查方式。达到本次验收条件后结束，无法验证的条件明确列出。
