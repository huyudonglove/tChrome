# 代码工程

用于阅读、修改和验证仓库代码。先明确用户要改变的行为、修改位置和验证方式；这些信息足够时就动手。第一次修改是待验证的实现，正确性要靠随后实际执行的检查确认，不需要在修改前靠推演消除全部不确定性。

## 用能力回答具体问题

| 当前问题 | 可用能力与下一步 |
| --- | --- |
| 不知道实现在哪里 | 用 local_fs_search 定位文件、local_fs_grep 检索符号或错误文本；大文件可用 local_fs_outline 看结构 |
| 缺少某段原文 | 用 local_fs_read 读取相关范围；已返回的内容沿 callId 用 evidence_search 取回，按 blockId 读块或 keyword 搜索 |
| 已知修改位置和预期行为 | 用 local_replace_block 做局部替换，或通过已加载的宿主执行工具应用局部补丁 |
| 不确定改动是否越界 | 查看 git diff，对照用户要求和修改前已有差异 |
| 不确定类型、调用契约是否成立 | 运行项目的类型检查或相关集成测试 |
| 不确定实际行为 | 运行定向测试、最小复现或相关页面操作，比较预期和结果 |

按需用 catalog_add 加载动态工具，取得 schema 后按实际参数调用。复用 workspace 中已有结论，并参考动态 <runtimeNotices> 提醒。

遇到专项问题时可从动态技能清单选用方法：疑难因果用 hypothesis-testing，网络状态用 network-state-troubleshooting，源码与页面不一致用 repo-browser-dual-audit。用 skill_load 加载所需正文；清单缺少线索时用 skill_list 查找。方法已经明确时直接执行，不把加载全部技能作为前置步骤。

## 读取到能够执行

- 阅读服务于具体决定：改哪个条件、谁消费返回值、异步调用在哪里等待。每次补读应说明缺少的事实怎样影响下一步。
- 读取目标逻辑及本次修改涉及的输入、输出或调用点；只有证据指向更广影响时才扩展范围。不按固定行数判断信息是否完整。
- evidence_search 不带 blockId 或 keyword 时返回根目录；目录块用于定位，内容块用于取原文。块属于对应来源快照，源文件已改变时读取当前受影响范围。
- 已知位置、目标行为和验证入口后，实施能够独立检查的部分。尚未弄清的另一部分不必阻塞它；只在缺口会改变当前修改决策时继续调查。

## 修改与反馈

1. 查看工作区现有改动，识别需要保留的用户内容；不要求工作区干净，也不自行 stash 用户工作。
2. 保持改动符合已确认设计和项目风格。局部修改用局部补丁；local_replace_block 默认 expectedMatches=1，匹配失败时根据实际匹配结果修正目标上下文，不猜测原文，也不反复重读无关代码。
3. 检查修改后的差异并运行适合该改动的验证。发现失败后，先区分实现问题、测试夹具问题与环境问题，再据此修正并重跑相关检查。
4. 若实现方向错误，撤回自己引入的具体改动后调整方案；保留用户已有内容，不用整文件恢复命令抹掉混合改动。

## 验证到目标成立

- 优先复用能覆盖目标行为的定向测试或复现。实际故障缺少覆盖时补回归用例；可先定位失败断言，也可在实现后补充并核验它能识别该故障。
- 局部行为用定向测试；跨文件接口用类型检查和关联集成测试；共享基础能力、扩展构建或项目明确要求的检查，按影响范围执行。验证范围取决于风险和仓库要求，不按固定耗时分级。
- 测试工具提供结构化汇总时，先用它定位失败，再读取相关输出。测试命令以当前仓库提供的入口为准。
- 测试应控制影响结果的初始状态，根据项目约定和配置构造输入，使失败能归因到待验证的行为。
- 工具写入成功只证明改动已应用。交付说明实际验证了什么、结果如何，以及仍未验证的部分；不要假设后面会有人或系统自动替你验证。
