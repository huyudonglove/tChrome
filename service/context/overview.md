# 总纲

请求进入后，Runtime 组装规则和工作状态，模型据此选择工具；执行结果更新上下文，供下一次判断，形成“理解请求 → 行动 → 读取结果 → 继续或结束”的循环。

这份上下文分为两部分：System 保存持续适用的规则及各模块的用法，User 保存本轮材料。下方栏目清单是模块职责的唯一导航；我按当前问题读取相关模块，不逐项填空。

工作材料围绕任务相互衔接：请求和目标确定方向，页面观察与工具记录提供执行证据，笔记承接中间工作，记忆保留需延续的信息。

执行循环还包含以下处理路径：

- **压缩**：Runtime 在每次发送主模型前检查上下文容量，达到阈值时先暂停主任务，请压缩 Agent 整理历史轮次；必要时继续整理当前轮较早片段和已有摘要。原始记录保留，摘要进入 #conversationHistorySummary，重新组装上下文后继续任务。
- **信息裁剪**：压缩后仍超限时，Runtime 优先将 notes 正文完整保存到本地文件，再按需要处理其他大块材料，将本次输入中的正文替换为文件引用。这减少的是模型窗口中的内容，不是删除原始数据；按 #environment 的读取方式取回所需部分。
- **查询**：摘要不足以支持判断时，模型通过 context.query 发起回查。查询 Agent 从指定摘要来源中选择相关轮次，Runtime 将对应原文放入 #currentQuery；此前查询进入 #queryHistory。查询结果可以分页，补充的证据重新参与后续行动。
- **报错与恢复**：参数校验失败或工具执行失败进入 #toolIO，模型结合诊断、恢复建议和工具定义修正下一步。传输层按统一策略处理可重试故障；压缩和查询保留底层失败原因。恢复后继续原任务，连续无效提交达到上限、无法恢复或用户停止时结束本轮，并保留执行记录。

这些路径共用同一份任务状态：压缩和裁剪改变可见材料，查询补回证据，错误反馈帮助调整行动。具体阈值、分页字段和恢复规则以对应模块为准。相关模块为空，只表示当前未提供材料，不证明历史中从未出现相关信息。
